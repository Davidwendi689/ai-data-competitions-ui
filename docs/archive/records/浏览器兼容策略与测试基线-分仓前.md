# 浏览器兼容策略与测试基线

本文描述完整平台产品与 Web 体验。物理拆分后，页面/组件/SSR/BFF 与浏览器配置归[唯一 Web](https://github.com/gduf-community/ai-data-competitions-ui)，本仓只保留可信 API；职责与证据见[运行拆分](https://github.com/gduf-community/competition-Q-A-website/blob/d9a789baed9f45ce033f97da5c627eb4cbcc8dee/docs/Web与API运行拆分.md)。

最后更新：2026-10-02

共享 JSON 请求通过 `signal.aborted` 检查取消，缺少 `reason` 时生成 `AbortError`，不要求 `throwIfAborted`；比赛新建编辑器用默认值工厂生成独立数组，不要求 `structuredClone`。回归测试显式移除这两项 API，覆盖正常请求、取消和新建表单默认值隔离。这是 API 兼容回归证据，不能代替 Safari/微信真机验收；当前文档声明与 Next.js 16/Tailwind 4 的完整浏览器运行基线仍需单独核对。

## 1. 文档目标

本文件用于明确本项目的浏览器支持边界、兼容性开发约束与验收顺序。

目标不是“兼容所有浏览器”，而是围绕本项目的真实用户路径做有限投入：

- 学生主要在手机端访问比赛详情、通知、报名页
- 链接传播高度依赖微信生态
- 老师和管理员主要在电脑端处理审核、导出和配置

因此，兼容策略必须优先服务这条主路径：

**学生在微信里打开链接浏览并报名，老师在电脑 `Chrome / Edge` 里管理比赛。**

## 2. 支持边界

### 2.1 当前结论

- 不支持 `IE`，不为 `IE 11` 做任何兼容适配。
- 不追求“所有国产浏览器逐一深度适配”，而是按用户路径分层验收。
- 公开页和报名链路必须优先保证移动端体验。
- 管理后台优先保证桌面端 `Chrome / Edge` 体验，移动端只要求基本可读、基本可操作。

### 2.2 验收优先级

### 第一优先级：必须兼容

- `Chrome` 桌面端
- `Edge` 桌面端
- `iPhone Safari`
- `Android Chrome`
- 微信内置浏览器：`iOS 微信`、`Android 微信`

### 第二优先级：基本可用

- `QQ 浏览器`
- `夸克浏览器`
- `UC 浏览器`
- `360 浏览器`

### 第三优先级：不作为重点适配对象

- `Firefox`
- `macOS Safari`
- 老安卓浏览器
- `IE`

说明：

- `Firefox` 与 `macOS Safari` 不作为本项目发布前的重点逐页验收对象，但公共页面和基础交互仍应尽量保持无明显功能性错误。
- 第二、第三优先级浏览器如出现轻微样式差异，不自动视为阻塞发布；若影响登录、报名、上传、审核等核心链路，则仍需处理。

### 2.3 工程支持声明

建议对外和对内统一使用以下支持声明：

```text
不支持 IE。

桌面端：
重点支持最近 2 个大版本的 Chrome、Edge。
对最近 2 个大版本的 Safari、Firefox 保持基础可用，但不作为主验收浏览器。

移动端：
目标为 iOS Safari 15+；Android 按实际 Chrome/WebView 引擎版本验收，系统 Android 8 不等于 Chrome 8。

国内场景：
保证微信内置浏览器可正常浏览、登录、报名、提问、上传基础附件。

后台：
主要保证 Chrome / Edge 桌面端体验，移动端做到基本可用即可。
```

## 3. 兼容判断依据

### 3.1 浏览器份额参考

本项目兼容边界主要参考中国用户场景，而不是全球平均分布。

根据 `StatCounter` 中国区数据：

- 中国全平台浏览器份额（`2026-04`）中，`Chrome`、`Edge`、`Safari` 仍是主要浏览器。
- 中国移动端浏览器份额（`2026-04`）中，`Chrome`、`Safari`、`UC Browser`、`Android Browser`、`Edge`、`QQ Browser` 均有一定占比。

这些数据不能等同于学院内真实设备分布，但足以支持以下结论：

- `Chrome / Edge / iPhone Safari / Android Chrome / 微信内置浏览器` 必须优先测试
- `QQ / 夸克 / UC / 360` 适合作为次级验收对象

### 3.2 Web 标准采用原则

涉及新 Web 特性时，优先使用 `MDN Baseline` 作为第一层筛选标准：

- `Baseline` 用于判断某项 Web 平台特性是否已经在主流浏览器中稳定可用
- 仅满足 `Baseline` 仍不代表一定适用于操作系统 `WebView`
- 微信内置浏览器属于必须额外真机验证的高风险环境，不能只看标准兼容表

因此，本项目采用以下判断顺序：

1. 先看该特性是否属于 `Baseline widely available`
2. 再判断是否落在微信 WebView、旧安卓设备、移动端表单场景等高风险区域
3. 若涉及核心链路，则必须做真实浏览器或真实设备验证

## 4. 开发约束

### 4.1 CSS 与布局

可以放心使用：

- `Flex`
- `Grid`
- 常规断点响应式布局
- 常规过渡、阴影、圆角、透明度

需要谨慎引入的新特性：

- `:has()`
- `subgrid`
- `container queries`
- `view-transition`
- 高级滚动驱动动画
- 强依赖新视口单位或新滚动时间线的效果

规则：

- 涉及新 CSS 特性时，优先确认 `MDN Baseline` 状态
- 若该特性不稳定或 WebView 风险高，核心页面必须有降级方案
- 后台页不要为了视觉效果引入会增加兼容成本的实验性布局能力

### 4.2 移动端尺寸基线

至少覆盖以下宽度进行布局检查：

- `375px`：小屏手机
- `390px`：常见 iPhone
- `414px`：大屏 iPhone
- `768px`：平板 / 窄屏
- `1280px`：普通笔记本
- `1440px`：常见桌面屏

移动端高风险问题：

- 按钮点击区域过小
- 表格横向溢出
- 弹窗超出屏幕
- 底部按钮被 `iPhone` 安全区遮挡
- 输入框聚焦后页面被键盘顶乱
- `100vh` 在手机浏览器中的高度异常

建议默认约束：

```css
min-height: 100dvh;
padding-bottom: env(safe-area-inset-bottom);
```

### 4.3 JavaScript 语法与浏览器 API

`Next.js + React` 会处理一部分语法转译，但不会自动为所有运行时 API 提供稳定兜底。

重点检查以下能力：

- `fetch`
- `URL` / `URLSearchParams`
- `Intl.DateTimeFormat`
- `ResizeObserver`
- `IntersectionObserver`
- `Clipboard API`
- `Web Share API`
- `File API`
- `localStorage` / `sessionStorage`

规则：

- 运行时 API 必须按“可用性检测 + 降级处理”设计
- 涉及复制、分享、下载、上传、持久化缓存时，不能假设所有移动浏览器都表现一致
- 微信内置浏览器、旧安卓浏览器和隐私模式是重点异常来源

### 4.4 微信内置浏览器

如果项目的传播路径依赖微信群、公众号、老师转发，微信 WebView 的优先级高于 `Firefox`。

必须专项验证：

- 微信内能否正常登录
- 微信内能否上传文件
- 微信内能否下载附件
- 微信内能否复制链接
- 微信内表单提交是否正常
- 微信内页面刷新后状态是否丢失
- 微信内返回上一页是否错乱
- 微信内是否命中旧版静态资源缓存

与微信相关的实现提醒：

- 不要把关键交互只建立在某一个新 API 成功的前提上
- 对复制链接、附件下载、外链跳转准备明确 fallback
- 核心提交流程必须减少对前端临时存储的强依赖

### 4.5 Cookie、登录态与鉴权

如果项目使用 `Auth.js`、`JWT`、`Cookie` 或后续接入 `Supabase` 等外部认证服务，重点关注：

- `SameSite`
- `Secure`
- `HTTP / HTTPS` 混用
- 跨域请求是否携带 `Cookie`
- 微信内置浏览器是否保留登录态
- `Safari` 是否拦截跨站 `Cookie`
- 刷新页面后 `session` 是否恢复

规则：

- 登录态丢失优先排查 `Cookie`、域名、协议、跨域和 WebView 存储策略
- 不要把这类问题误判为数据库或业务逻辑错误
- 涉及鉴权问题时，桌面浏览器与微信 WebView 必须分开验证

### 4.6 表格与后台页面

本项目后台页大概率长期包含：

- 比赛管理
- 报名审核
- 通知管理
- 用户管理
- 日程管理

兼容规则：

- 普通用户页面：必须移动端友好
- 管理后台页面：优先桌面端体验，可接受移动端基本可用
- 复杂表格在手机端优先改成卡片列表，不要硬塞横向大表格

例如报名审核：

- 桌面端可使用高密度表格
- 移动端应切换为卡片摘要 + 操作按钮
- 重要操作按钮应避免放在横向滚动区域的最右侧

### 4.7 构建与配置

`Browserslist` 应作为前端兼容配置的统一入口，供 `Autoprefixer`、`Babel`、`PostCSS`、`ESLint`、`Webpack` 等工具共享目标浏览器范围。

建议配置：

```json
{
  "browserslist": {
    "production": [
      "> 0.5%",
      "last 2 versions",
      "not dead",
      "not IE 11",
      "iOS >= 15",
      "Android >= 8"
    ],
    "development": [
      "last 1 chrome version",
      "last 1 edge version",
      "last 1 safari version"
    ]
  }
}
```

若后续确认校内存在较多旧安卓设备，可评估放宽为：

```json
"Android >= 7"
```

但不建议继续下探到更老版本，否则会显著拉高开发与测试成本。

当前仓库状态说明（`2026-09-14`）：

- `package.json` 已声明上述 `browserslist` 生产与开发范围。
- 该配置表示编译目标基线，不等于各页面已经完成真实设备或浏览器验收；执行记录仍应按本文清单留证。

- `/clubs`

- `/sign-in`
- `/sign-up`
- `/forgot-password`
- `/me/applications`

重点关注：

- CTA 按钮可点击性
- 表单输入与校验反馈
- 附件上传与下载
- 登录态保持

### 5.2 管理后台页面

以下页面优先做桌面端兼容验收：

- `/admin`
- `/admin/competitions`
- `/admin/applications`
- `/admin/notices`
- `/admin/users`
- `/admin/schedule`
- `/admin/clubs`
- `/admin/clubs/reviews`
- `/admin/security/situation`

重点关注：

- `Chrome / Edge` 下布局稳定
- 表格、筛选器、弹层、抽屉和批量操作正常
- 导出、下载、刷新、分页、状态切换不异常
- 窄屏下至少可读，避免操作完全失效

### 5.3 核心业务链路

发布前至少保证以下链路在第一优先级浏览器中可用：

1. 浏览比赛列表与详情
2. 登录 / 注册 / 找回密码
3. 学生提交报名
4. 上传基础附件
5. 提交后刷新页面并恢复状态
6. 管理员审核通过 / 驳回
7. 管理员导出数据
8. 学生在微信里打开链接并完成基础报名动作

## 6. 测试顺序

不建议一开始就大规模投入真机池，先按以下顺序推进：

1. `Chrome DevTools` 响应式模式
2. `Edge` 桌面端真实访问
3. `iPhone Safari` 真机
4. `Android Chrome` 真机
5. 微信内置浏览器真机
6. `QQ / UC / 夸克 / 360` 做次级验收

说明：

- `Chrome DevTools` 只能用于快速发现布局问题，不能替代真机验收
- 微信、`iOS Safari`、文件上传下载、登录态恢复，必须至少做一次真实设备验证

## 7. 发布阻塞项

出现以下问题时，应视为阻塞发布：

- `Chrome / Edge` 桌面端后台核心操作不可用
- `iPhone Safari` 或微信内置浏览器无法登录
- 移动端报名表无法提交
- 附件上传或下载失败
- 刷新页面后登录态或报名状态异常丢失
- `375px / 390px` 下关键按钮、弹窗或表单严重溢出
- 静态资源缓存导致微信长期命中旧版 `JS / CSS`

以下问题默认不阻塞发布，但应记录并排期：

- 次级浏览器存在轻微样式差异
- 非核心动画效果退化
- 管理后台在手机上体验一般但仍可完成基本操作

## 8. 后续落地建议

建议按以下顺序推进兼容建设：

1. 在 `package.json` 中补充 `browserslist`
2. 为移动端页面补齐 `375 / 390 / 414 / 768` 宽度检查
3. 为报名链路补齐微信真机测试记录
4. 对上传、下载、复制、分享、存储等高风险能力增加 fallback
5. 将兼容性回归项纳入发布前检查清单
