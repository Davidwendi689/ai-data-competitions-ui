## 1. 背景

当前项目已经存在多种形式的“搜索”，但它们之间没有形成统一的搜索领域模型。

公开比赛列表目前采用前端本地过滤：

```ts
competition.title.includes(keyword) ||
competition.category.includes(keyword) ||
competition.department.includes(keyword)
```

数据首先通过 `/api/competitions` 全量返回浏览器，再由前端执行筛选。这种方式在当前数据规模下可以工作，但存在明显限制：

* 搜索逻辑散落在页面组件中；
* 无分页搜索能力；
* 无统一相关度排序；
* 无搜索建议与搜索历史；
* 无法自然扩展到问答、经验帖、公告等资源；
* 数据规模扩大后需要向浏览器传输越来越多无关数据；
* 不同模块容易分别实现自己的搜索逻辑，最终形成多套互不兼容的搜索系统。

另一方面，管理员后台已经存在一套相对成熟的 PostgreSQL 搜索基础设施：

```text
PostgreSQL
    +
pg_trgm
    +
GIN trigram index
    +
ILIKE
    +
similarity()
    +
server-side pagination
```

相关代码主要位于：

```text
src/lib/admin-search/
src/app/api/admin/search/
src/lib/db/migrations/0017_add_admin_search.sql
```

因此，本项目不需要再引入 Elasticsearch、Meilisearch、Typesense 等独立搜索服务。

本次设计目标是在现有 PostgreSQL 基础设施上建立统一的公共搜索系统，并参考 Animeko 的搜索架构改进查询模型、状态管理和前端交互。

参考项目：

```text
https://github.com/open-ani/animeko
```

## 2. Animeko 搜索架构

Animeko 的搜索链路大致为：

```text
SearchPage
    ↓
SearchViewModel
    ↓
SubjectSearchQuery
    ↓
SubjectSearchRepository
    ↓
AniSubjectSearchService
    ↓
Ani API
```

需要注意的是，Animeko 客户端本身并不负责实现最终的搜索相关度算法。

客户端主要负责：

* 查询状态；
* 搜索条件建模；
* 搜索历史；
* 搜索建议；
* 筛选；
* 排序；
* 分页；
* 搜索生命周期；
* UI 状态切换。

真正的相关度搜索由远端 Ani API 完成。

因此，本项目需要借鉴的是 Animeko 的搜索产品架构，而不是直接移植其后端实现。

## 3. 可借鉴的核心设计

### 3.1 Query Object

Animeko 没有把搜索表达为简单的：

```ts
search("keyword")
```

而是使用一个完整的结构化查询对象：

```text
keywords
type
tags
year
season
rating
nsfw
sort
```

本项目应采用相同的设计思想。

建议统一定义：

```ts
export interface SearchQuery {
  q: string;

  types?: SearchEntityType[];

  competitionId?: string;
  year?: number;
  category?: string;
  status?: string;

  sort?: SearchSort;

  page: number;
  pageSize: number;
}

export type SearchEntityType =
  | "competition"
  | "question"
  | "experience"
  | "notice"
  | "club";

export type SearchSort =
  | "relevance"
  | "newest"
  | "popular";
```

由查询对象统一负责：

* 参数归一化；
* 搜索条件；
* 筛选状态；
* 排序状态；
* 分页状态。

页面组件不再自行维护搜索业务逻辑。

---

### 3.2 编辑状态与提交状态分离

搜索输入框需要区分：

```text
editingQuery
```

和：

```text
committedQuery
```

用户输入：

```text
数
数学
数学建
数学建模
```

不应该每输入一个字符就触发一次完整搜索。

输入阶段主要用于：

```text
Suggestion
```

正式搜索应仅在以下行为发生时执行：

* Enter；
* 点击搜索按钮；
* 点击搜索建议；
* 修改需要立即刷新的筛选条件。

这种设计可以显著降低无意义请求，同时避免页面结果不断跳动。

---

### 3.3 搜索状态

建议将搜索分为：

```text
Idle
Searching
Success
Empty
Error
```

同时支持：

```text
History
Suggestion
Result
```

三种数据视图。

交互关系：

```text
搜索框为空
    ↓
显示历史记录

搜索框非空但尚未提交
    ↓
显示搜索建议

提交搜索
    ↓
显示正式搜索结果
```

---

### 3.4 Debounce

Animeko 当前对搜索建议使用约 800 ms debounce。

Web 场景无需设置这么长，建议：

```text
250–400 ms
```

推荐默认：

```text
300 ms
```

搜索建议属于轻量请求，应尽量保持响应迅速。

---

### 3.5 取消旧请求

新搜索开始时，应取消旧请求，避免请求乱序导致旧结果覆盖新结果。

React 侧可以直接使用：

```ts
AbortController
```

搜索生命周期：

```text
Query A
    ↓
请求 A

用户提交 Query B
    ↓
abort A
    ↓
清理或冻结旧状态
    ↓
请求 B
    ↓
更新结果
```

现阶段无需为了这一需求额外引入 TanStack Query。

# 12. 搜索历史

第一阶段不建议建立数据库表。

优先使用：

```text
localStorage
```

例如：

```ts
interface SearchHistoryItem {
  query: string;
  searchedAt: number;
}
```

限制：

```text
最多保留 10–20 条
```

需要：

* 去重；
* 最近搜索置顶；
* 支持单条删除；
* 支持全部清除。

后续如果确实需要多端同步，再增加账号级搜索历史。

# 15. `/competitions` 页面改造

目前：

```text
GET /api/competitions
        ↓
下载所有比赛
        ↓
useMemo
        ↓
.includes()
```

最终应改为：

```text
GET /api/search
    ?type=competition
    &q=...
    &year=...
    &status=...
    &page=...
```

公开比赛页面仍然可以保留自己的视觉布局，但数据访问统一进入 Search Domain。

这样：

```text
Navbar global search
/search
/competitions
competition question search
```

最终全部共享一套搜索基础设施。

# 17. 前端状态控制器

建议增加：

```text
src/hooks/use-search-controller.ts
```

大致职责：

```ts
interface SearchController {
  editingQuery: string;
  committedQuery: string;

  suggestions: SearchSuggestion[];
  results: SearchResult[];

  loadingSuggestions: boolean;
  loadingResults: boolean;

  setEditingQuery(value: string): void;
  submit(): void;
  clear(): void;
}
```

内部管理：

```text
debounce
AbortController
history
suggestion request
formal search request
```

搜索 UI 不直接处理网络生命周期。

# 20. 许可证边界

Animeko 使用：

```text
GNU AGPLv3
```

本项目应借鉴：

* 查询对象设计；
* 搜索状态模型；
* 搜索历史；
* Suggestion；
* debounce；
* 请求取消；
* Filter；
* Sort；
* Pagination；
* UI 交互思想。

不建议直接复制 Animeko 的 substantial source code。

原因：

1. 技术栈本身不同：

   ```text
   Kotlin Compose
   →
   React / Next.js
   ```

2. 直接复制源码会带来 AGPL 许可证义务。

因此应重新实现相同设计思想，而不是进行源码移植。
